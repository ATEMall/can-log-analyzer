## 1. 产品概述

### 1.1 产品定位

一款**完全离线、本地运行**的智能汽车通信日志分析桌面工具。以"加载日志 → 关联数据库 → 一键解码 → 可视化与导出"为核心闭环，覆盖 CAN / CAN FD / LIN / 车载以太网等主流车载总线，并在其上提供 UDS 诊断、XCP 标定等常用高层协议解析能力。

关键词：**离线、轻量、准确、开箱即用**。不依赖云、不依赖商业授权、不要求用户懂编程。

### 1.2 目标用户

| 用户角色 | 场景 | 核心诉求 |
|---|---|---|
| 汽车电子测试工程师 | 台架 / 实车 HIL、BMS、ADAS、EMB 测试日志分析 | 快速定位报文与信号，核对物理值是否正确 |
| 标定工程师 | XCP 标定数据回放、A2L 变量核对 | 标定参数变化曲线与数值验证 |
| 诊断工程师 | UDS 诊断会话抓包分析 | 请求/响应配对、DID/DTC 解析 |
| 嵌入式 / 总线开发工程师 | 调试 CAN 矩阵、验证 DBC | 字节序、位布局、因子偏移核对 |
| 学生 / 个人开发者 | 学习总线协议 | 低成本、无授权门槛的入门工具 |

### 1.3 核心价值主张

1. **零门槛**：绿色便携版单文件运行，无需安装、无需 license、无需联网。
2. **可信赖**：解码结果与行业权威实现（cantools / Vector 语义）对拍一致，字节序、因子偏移、有符号数均正确。
3. **多协议**：一套工具覆盖 CAN / LIN / 车载以太网，以及 UDS / XCP 高层协议，替代多套工具。
4. **可回放**：物理量 ↔ 报文双向转换，支撑 HIL 仿真激励与标定验证。

### 1.4 竞品与差异化

| 竞品 | 类型 | 劣势（本产品机会点） |
|---|---|---|
| Vector CANoe / CANalyzer | 商业旗舰 | 授权昂贵、链路复杂、绑定硬件，学习成本高 |
| TSMaster（同星） | 国产商业 | 功能全但偏重在线采集与硬件绑定，离线轻量分析体验重 |
| Intrepid Vehicle Spy | 商业 | 授权费高，离线分析非主打 |
| BUSMASTER | 开源 | 年久失修，UI 老旧，仅 CAN |
| SavvyCAN | 开源 | 仅 CAN/CAN FD，无 LIN/以太网/UDS 深度解析 |
| cantools | Python 库 | 无界面，需编程 |

**差异化定位**：面向工程师个人的、多协议、离线、带友好界面的免费分析工具，能力对标"轻量版 CANalyzer + 部分 VSpy"，体验对标现代桌面应用。

## 2. 现状评估（v2.0.0 基线）

### 2.1 技术栈

| 层 | 技术 |
|---|---|
| 桌面框架 | Electron 28 |

| 发布 | Windows NSIS 安装版 + Portable 便携版 |

### 2.2 已实现能力

- ASC / BLF 日志解析（普通 CAN 与 CAN FD，含 64 字节）
- DBC 数据库加载与信号级解码（Intel / Motorola、factor/offset、有符号、VAL_ 枚举）
- 三视图呈现：数值表格 + 曲线图（缩放/平移/图例显隐）+ 位布局视图
- CAN 报文日志（过滤、行内解码、导出 ASC）
- 物理量 CSV → ASC 反向生成报文（含 CRC8/CRC16 系列）
- ASC → BLF 格式转换
- 内置使用手册、原生应用菜单、About 弹窗
- 单元测试 49 项（7 个测试文件）

### 2.3 验收测试发现的关键缺陷（2026-08-29）

> 完整测试过程见 `docs/ACCEPTANCE-2026-08-29.md`。

1. **[P0] Motorola（大端）字节序信号解码完全错误**。用 cantools 43.0.2 作为参考实现对拍：13 个信号中，10 个 Motorola 信号 100% 解码错误，3 个 Intel 信号 100% 正确。根因位于 `electron/dbc.js` `decodeSignalFrame()` 的 Motorola 位遍历逻辑（锯齿步进方向错误，导致信号位跨越错误字节且位序颠倒）。现有样例 DBC 全部为 Intel 字节序，构成测试盲区。**Motorola 在真实车辆 DBC（尤其 J1939 与多数 ECU 供应商）中极常见，此缺陷影响面大，必须作为最高优先级修复。**

2. **[P2] DBC 解析能力不完整**。不支持：`BA_` / `BA_DEF_` 属性（如 `GenMsgCycleTime` 周期、`VFrameFormat` 扩展帧标志）、`SIG_VALTYPE_` 值类型、多路复用信号的实际解码（当前仅存字符串不参与解码）、节点 `BU_` 完整建模、注释 `CM_` 关联展示。

3. **[P2] 扩展帧（29-bit ID）语义缺失**。BLF 层能解析 extended 标志，但 DBC 层无扩展帧标识建模（DBC 中依赖 `BA_ "VFrameFormat"=1`），导致扩展帧与标准帧无法正确区分。

4. **[P2] 架构债：全量 IPC 传输**。解码流程为"渲染进程把全部报文序列化后经 IPC 传给主进程，解码后再全量回传"。20 万帧（9.4MB）JSON 序列化约 86ms，尚可接受；但百万级日志会触发内存峰值与主进程阻塞，存在崩溃风险。需重构为分块/流式解码。

### 2.4 技术债清单

| 编号 | 债务 | 影响 | 处置 |
|---|---|---|---|
| TD-1 | 全量 IPC 传数组 | 大文件崩溃风险 | v2.1 重构 |
| TD-2 | Motorola 解码错误 | 结果错误 | v2.1 修复（P0） |
| TD-3 | DBC 解析不完整 | 部分 DBC 无法正确解码 | v2.1/v2.2 |
| TD-4 | 无工程保存/恢复 | 每次重开需重配 | v2.1 |
| TD-5 | 无配置持久化 | 用户偏好丢失 | v2.1 |
| TD-6 | 单窗口、无深色模式 | 体验受限 | v2.2 |
| TD-7 | 无日志/错误上报 | 问题难复现 | v2.2 |
| TD-8 | 测试覆盖率低（仅 1 个后端测试文件 + 6 组件） | 回归风险高 | 持续 |

## 7. 测试与验收标准

### 7.1 测试策略

| 层 | 方法 | 工具 |
|---|---|---|
| 解析器对拍 | 与 cantools（DBC）、官方样例（BLF/LDF/PCAP）逐一比对 | Python cantools + Node 脚本 |
| 单元测试 | 每个解析函数独立用例，覆盖边界（位边界、字节序、有符号、64 字节） | Vitest |
| 组件测试 | 关键 UI 组件渲染与交互 | Testing Library |
| 性能测试 | 大数据量（10 万 / 100 万帧）加载与解码耗时基准 | 脚本 |
| 端到端验收 | 真实样例（含 Motorola、LIN、UDS 抓包）完整流程走查 | 人工 + 冒烟脚本 |

### 7.2 对拍基准

- DBC 信号解码：以 cantools 为权威参考，**Motorola / Intel / 有符号 / 枚举 / 多路复用 100% 一致**（当前 Motorola 不达标，见 ACCEPTANCE 报告）。
- BLF 解析：以 python-can 生成的 BLF 为标准往返验证。
- ASC 解析：与 Vector / TSMaster 实际导出样例对比。

### 7.3 每版本验收门槛（DoD）

交付一个版本，必须同时满足：

1. 全部单元测试通过，且**新增功能有对应用例**。
2. 关键解析器通过 cantools / 官方样例对拍（0 不一致）。
3. 性能基准不劣化（记录到验收报告）。
4. CHANGELOG 更新，版本号符合 semver。
5. 产出 Windows 安装版 + 便携版，均可正常启动。
6. PM 依据本验收标准实测通过后，方视为"验收通过"。
