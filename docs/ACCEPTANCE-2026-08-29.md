## 4. 关键缺陷详情

### [P0] Motorola 字节序解码完全错误

**现象**：自建 DBC（13 个信号，10 个 Motorola + 3 个 Intel）与 cantools 逐帧对拍，10 个 Motorola 信号**全部**解码错误，3 个 Intel 信号全部正确。

**证据（节选，期望值来自 cantools）**：

| 信号 | 布局 | 数据 `12 34 56 78 9A BC DE F0` | 期望 | 实际 |
|---|---|---|---|---|
| M_MotA | `0\|16@0+` | — | 6699 | 5685 |
| M_MotC | `7\|8@0+` | — | 18 | 72 |
| M_MotI | `0\|1@0+` | `80 00 00 00 00 00 00 00` | 0 | 1 |
| M_IntelA | `0\|16@1+` | — | 13330 | 13330 ✅ |

**根因定位**：`electron/dbc.js` → `decodeSignalFrame()` → Motorola 分支：

```js
// 当前错误实现
if ((bitPos % 8) === 0) {
  bitPos += 15;
} else {
  bitPos--;
}
```

该锯齿步进方向错误，导致信号位跨越错误字节、位序颠倒（如 `0|16` 的 16 位信号本应落在 byte0+byte1，实际跨到 byte0+byte1+byte2）。正确语义应为从 MSB 位置单调递增遍历位。

**影响面**：Motorola 是大端字节序，在真实车辆 DBC 中非常常见（J1939、大量 ECU 供应商默认采用 Motorola）。当前所有此类信号解析结果错误。

**未暴露原因**：`TestExample/` 三个样例 DBC 的信号**全部为 Intel（@1）**，无一个 Motorola 用例，构成测试盲区。

**处置建议**：v2.1 最高优先级修复；修复后立即补 Motorola 对拍测试（以 cantools 为基准），并新增含 Motorola 信号的样例数据。

## 5. 能力缺口（非阻塞，纳入路线图）

| 编号 | 缺口 | 优先级 |
|---|---|---|
| GAP-1 | DBC `BA_` / `BA_DEF_` 属性解析缺失（周期、扩展帧标志、发送类型） | P1 |
| GAP-2 | 扩展帧（29-bit）语义未建模（依赖 `VFrameFormat`） | P1 |
| GAP-3 | 多路复用信号不参与解码 | P1 |
| GAP-4 | `SIG_VALTYPE_` 值类型不支持 | P1 |
| GAP-5 | 全量 IPC 传输，大文件内存风险 | P1 |
| GAP-6 | 无工程保存/恢复、无最近文件 | P1 |
| GAP-7 | LIN / UDS / XCP / 车载以太网 尚未支持 | 中远期 |

## 6. 验收结论与建议

1. **当前版本对纯 Intel DBC 场景可用**，对含 Motorola 信号的场景**解码结果不可信**，需在发布说明与 README 中显式标注，或尽快发布 v2.1 修复。
2. 建议将本报告中的 P0 缺陷转为 GitHub Issue 跟踪（见 Issue 提交）。
3. 后续每个版本发布前，PM 将执行同样的对拍测试，并以此报告格式留存验收记录。
